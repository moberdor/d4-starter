## Target

A purple worm with a glowing tail crawls around a garden at night while eating fireflies. Playing the game should feel relaxed at first and more tense as the worm gets longer. The grid is 24x24.

## Where things live

The `core/` folder contains the game rules.
The `app/` folder handles graphics, player input and displaying the game.
The `tests/` folder contains automated tests.
The `tools/` folder contains scripts that generate the 3D models.
The app displays the results of events handled by the core

## Adding a tile kind

To add a tile kind, we first add its definition to Board.TILES in `core/board.gd`. Next, we create its 3D model in `tools/build_art.py` and register it in the tile builders. Then, we run deno task art to generate the updated models and deno task kit to inspect them.

## Patterns, and what they bought us

Separation of concerns keeps game rules in `core/` folder and graphics in `app/` folder to make the rules easier to test.

The Command Queue pattern stores upcoming movement and directions so quick key presses do not break movement.

Data driven design keeps tile definitions separate from their 3D models to make the project easier to build upon.

## One idea we carried over

- **The problem:** Mixing game rules with graphics makes code more difficult to test and maintain.
- **The practice:** We separated game logic from the user interface as we did in our TypeScript projects.
- **The mechanism:** Godot uses GDScript classes in `core/` to handle game rules independently of scene nodes while the `app/` folder handles visuals and input. This makes game testing easier, but requires keeping Godot dependencies out of the `core/`
